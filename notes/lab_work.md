# Java Virtual Threads — лабораторная

## Цель

На коде понять, где virtual threads помогают backend-приложению, а где нет: blocking I/O, carrier threads, concurrency и CPU-bound вычисления.

## Карта понятий

```text
Много virtual threads
        │ JVM планирует выполнение
        ▼
Небольшое число carrier threads
        │ platform / OS threads
        ▼
Ограниченное число CPU-ядер
```

- **Task** — `Runnable`, отправленный в `ExecutorService`.
- **Platform thread** — обычный Java-поток, связанный с потоком ОС.
- **Virtual thread** — лёгкий поток, которым управляет JVM.
- **Carrier thread** — platform thread, временно исполняющий virtual thread.
- **Concurrency** — много незавершённых задач одновременно.
- **Parallelism** — реальное одновременное выполнение вычислений на CPU-ядрах.

## 1. Fixed pool и искусственное blocking I/O

**Код:** [`Lab_Main.java`](../src/main/java/org/Lab_Main.java). В начале опыта: 1 000 задач и `Thread.sleep(1_000)`.

| Размер fixed pool | Результат | Почему |
| --- | --- | --- |
| 10 | `PT1M40.450425S` | 1 000 / 10 = 100 волн; 100 × 1 секунда ≈ 100 секунд |
| 100 | `PT10.055032S` | 1 000 / 100 = 10 волн; 10 × 1 секунда ≈ 10 секунд |
| 1 000 | `PT1.054274S` | Все задачи почти одновременно начали ожидание |

Во время `sleep` CPU почти свободен. Но platform thread всё ещё занят текущей задачей и не может взять следующую из очереди. Это не lock на мониторе, а ожидание таймера при занятом worker thread.

### Мои выводы

> 1 000 задач / 10 потоков = 100 волн.

> Потоки ждут окончания `sleep`.

> При 100 потоках на 1 000 задач получается около 10 секунд.

> Обычный поток потребляет память, и это нужно учитывать.

### Почему 1 000 platform threads — не production-решение

Platform thread — поток ОС. Для большого числа таких потоков растут затраты на стек и native-ресурсы, создание и планирование, context switching; также появляются системные лимиты.

## 2. Virtual threads для ожидания

**Изменение:** `Executors.newVirtualThreadPerTaskExecutor()` создаёт одну virtual thread на каждую submitted task.

| Задач | Результат |
| --- | --- |
| 1 000 | `PT1.02615S` |
| 10 000 | `PT1.057976S` |
| 100 000 | `PT1.627245S` |

Когда задача дошла до `Thread.sleep`, JVM снимает ожидающий virtual thread с carrier thread. Carrier освобождается для другой готовой virtual-задачи. Ожидающая virtual-задача существует в памяти, но не удерживает отдельный OS thread.

`Thread.sleep` — имитация I/O, а не настоящее I/O. На 100 000 задач дополнительное время (~0.63 секунды) ушло на создание, планирование, park/unpark и завершение virtual threads; почти вся одна секунда ожидания перекрылась.

### Мои выводы

> Пока одни задачи ждут, выполняются другие — получается конвейер.

> Одна секунда нужна для сна, остальные миллисекунды — реальные затраты на организацию выполнения.

## 3. Virtual thread и carrier thread

**Код:** [`ThreadOutput_Main.java`](../src/main/java/org/ThreadOutput_Main.java)

Наблюдение для одной задачи:

```text
Task 00: before sleep — VirtualThread[#28]/runnable@ForkJoinPool-1-worker-1
Task 00: after sleep  — VirtualThread[#28]/runnable@ForkJoinPool-1-worker-4
```

`VirtualThread[#28]` — та же задача; после ожидания она продолжилась на другом carrier worker. Локальные переменные и состояние принадлежат virtual thread, а не конкретному carrier.

Часть `@ForkJoinPool-...-worker-N` — диагностическая строка текущей реализации JDK, не публичный API-контракт.

### Мои выводы

> Virtual thread не поменялся, сменился worker.

> Virtual thread сохранился; не важно, какой worker его несёт.

## 4. Настоящий blocking HTTP

**Код:** [`BlockingHttp_Main.java`](../src/main/java/org/BlockingHttp_Main.java)

20 virtual threads синхронно вызывают `HttpClient.send(...)` к endpoint с задержкой в одну секунду.

| Параметр | Результат |
| --- | --- |
| Задач | 20 |
| Успешных ответов | 20 × `HTTP 200` |
| Общее время | `2,75 seconds` |

`send(...)` остаётся blocking вызовом для конкретной задачи. Virtual threads не отменяют ожидание сети: они позволяют множеству задач ждать, не удерживая отдельный OS thread для каждой.

Результат не обязан быть ровно одной секундой: добавляются DNS, TCP/TLS, сеть, очередь и работа удалённого сервера, передача ответа и overhead JVM. Порядок напечатанных задач определяется временем получения ответов, а не номерами задач.

### Мои выводы

> Virtual threads помогают не удерживать OS thread во время blocking I/O.

## 5. CPU-bound: virtual threads не добавляют ядер

**Код:** [`CpuBoundMain.java`](../src/main/java/org/CpuBoundMain.java)

Каждая задача считает простые числа до `1_000_000`. В запуске было обнаружено 10 доступных процессоров.

| Количество задач | Fixed pool размером 10 | Virtual threads |
| --- | --- | --- |
| 32 | `0,35 seconds` | `0,32 seconds` |
| 320 | `2,70 seconds` | `2,59 seconds` |

Время выросло почти одинаково: задач стало в 10 раз больше, значит, примерно в 10 раз вырос общий объём вычислений. 320 virtual threads не означают 320 параллельно работающих CPU-задач: physical parallelism ограничен числом ядер.

Разница в сотые доли секунды не доказывает преимущество одной модели. Вторая реализация запускается в уже прогретой JVM: JIT мог скомпилировать горячий код, а кэши прогреты. Один запуск в одном JVM-процессе — не честный benchmark; для этого используют JMH и прогревочные итерации.

### Мои выводы

> Virtual threads используют carrier threads, а число ядер ограничено.

> Virtual threads подходят для I/O; для CPU-bound задач важно ограничивать параллелизм числом ядер.

## Практическое правило

| Тип нагрузки | Подход |
| --- | --- |
| Много одновременных HTTP/DB/file ожиданий | Virtual thread per task — хороший кандидат |
| Тяжёлые CPU-вычисления | Bounded executor около числа ядер; virtual threads сами ускорения не дадут |
| Смешанная задача | Разделить I/O и CPU-части; не создавать неограниченный CPU-параллелизм |

## Следующий эксперимент

1. В `CpuBoundMain` вызвать virtual-вариант первым, platform-вариант — вторым.
2. Запустить несколько раз и сравнить разброс результатов.
3. Затем сделать backend mini-task: параллельно загрузить I/O-зависимые источники через virtual threads, после чего ограниченно обработать CPU-часть.
